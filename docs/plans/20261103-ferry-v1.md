# ferry v1: a call bus between two hosts over one ssh stream

## Overview

ferry lets two hosts call named programs on each other when only one of them can open a connection to the other. One host, the dialer, runs `ssh <host> ferry peer` and keeps that one stream open. Over it either side calls a handler on the other side: an executable file the other side has registered by a marker comment. A call is a two-way byte stream with argv and an exit code, the same shape as `ssh host command`, so a caller pipes into it and reads its output like any local command.

The case it is built for: the far host accepts no inbound connections, and reaches the dialer only through an ssh reverse tunnel that the far host itself keeps up. The dialer's key for that tunnel cannot run commands. So the far host has no way to start anything on the dialer, and the dialer has to come to it. ferry keeps that boundary: the dialer runs only the names in its own handler folder, never a path or a command the other side sends.

A call can be entered two ways:

- `ferry call <name> [args...]` on either host. Its stdin, stdout and stderr are the call's streams, and its exit code is the handler's.
- A loopback TCP port, configured on the host that wants it. Every connection accepted on `127.0.0.1:<port>` becomes one call to a named handler on the other side, with the socket's bytes as the handler's stdin and stdout, the way inetd hands a socket to a program. This is how an HTTP client that only talks to loopback reaches a service behind the other host: the handler on the other side forwards the bytes. ferry itself knows nothing about HTTP.

### Non-goals for v1

- No queue, no retry and no history of calls. A call made while the link is down fails at once with code 255.
- No more than one dialer per far host. A new link replaces the old one.
- One handler name per file. No fixed arguments in the marker, no aliases.
- `ferry reload` re-reads the handler folder only. A change to `config.toml` needs a daemon restart.
- No call timeout. A call ends when the handler exits, the caller goes away or the link drops.
- No authentication beyond ssh, no encryption beyond ssh, no TLS on the loopback ports.
- No agent skill or Claude Code plugin in this repo yet.
- Listen ports bind `127.0.0.1` only, never another address.
- No Windows, no Intel Mac, no Linux ARM builds.

### Rejected alternatives

- **A separate ssh connection per call**, the way agterm opens a channel per HTML page. Every call would pay a new ssh handshake (0.15-0.18 s measured on a LAN) and the code would need two kinds of connection. The largest payload in the intended use is a few hundred KiB, which one stream carries in a handful of chunks.
- **ssh ControlMaster with one channel per call.** ssh would give per-channel flow control, but every call would add an ssh client process on the dialer, a process on the far side and a mux socket. That flow control buys nothing at these sizes.
- **No daemon on the far host**, with the process sshd starts doing everything. Calls start on the far host, so something there has to own a socket and the ports. If the sshd-spawned process owned them, the ports would exist only while the link is up, and on a reconnect the old and the new process would race for them.
- **systemd to start the far host's daemon.** The far host may run its user manager without lingering, and it may give no root. `ferry peer` starts the daemon itself when it finds none.
- **A built-in `http` handler type** with an upstream URL in the config. That makes ferry an HTTP proxy. A plain handler that forwards bytes keeps ferry protocol-agnostic.
- **Binary length-prefixed frames.** JSON lines can be read by eye while debugging. base64 costs a third more bytes, which does not matter at these sizes.
- **Threads instead of tokio**, as in the sibling projects foster and farside. Every blocking read would need its own wake-up pipe to be cancellable, and the writer's fairness and the timers would be hand-rolled.
- **Backing off to a 300-second cap.** When the far host is down the tunnel port on the dialer is closed, so a retry is refused by the dialer's own kernel in under a millisecond. A long cap would only delay recovery after the far host wakes.

## Solution Overview

The same binary runs on both hosts. Each host runs one `ferry daemon`. The two daemons are peers. They differ in one thing only: the dialer has `connect` in its config and opens the link, the far host waits for it.

```
dialer                                   far host
ferry daemon ── ssh -T <connect> ferry peer ──> sshd ── ferry peer (bridge) ── ferry daemon
   │  unix socket                                                              │  unix socket
   ├─ ferry call / ls / reload                               ferry call / ls / reload ─┤
   ├─ 127.0.0.1:<port> listeners                           127.0.0.1:<port> listeners ─┤
   └─ runs its own handlers                                       runs its own handlers ┘
```

- **The link.** On the dialer the link is the stdin and stdout of the ssh child process. On the far host it is the unix-socket connection of the `ferry peer` bridge. Above that both sides run the same session: `hello`, ping, calls.
- **The bridge.** `ferry peer` connects to the far host's daemon socket, says it is a peer, and copies bytes both ways between its stdio and the socket until either side ends. It writes nothing of its own to stdout. If no daemon answers, it starts one detached and waits for its socket.
- **One daemon per host.** The daemon holds an exclusive lock on `~/.local/state/ferry/ferry.lock` for its lifetime. A second daemon that cannot take the lock exits 0 at once, so two bridges racing to start one leave one running.
- **Calls.** Either side opens a call with `open {id, name, argv}`. The other side looks the name up in its own handler list, starts the file with argv and no shell, in `$HOME`, with the daemon's environment, and wires its stdio to `chunk` frames. A call always goes to the other side. A host never calls its own handlers through ferry.
- **Fairness and order.** One writer task owns the link's write half. Link frames (`hello`, `handlers`, `ping`) go first. Every frame of a call (`open`, `chunk`, `eof`, `exit`, `error`, `cancel`) goes through that call's own outbound slot, which holds one frame at a time, and the writer takes one frame from each call in turn. So the frames of a call leave in the order the call produced them, an `eof` or `exit` never overtakes the call's last `chunk`, and a large call gets ahead of a small one by at most one frame.
- **Back-pressure without stalling.** There is no flow control across the link. The reader never waits for a slow consumer: it appends inbound chunks to the call's buffer and counts the unread bytes, on both sides, stdin waiting for a handler as well as stdout and stderr waiting for a caller. A call whose unread bytes pass 16 MiB ends with 255 on both sides: the handler's side sends `error {code: 255, message: "unread limit"}` and stops the handler, the caller's side sends `cancel` and reports 255 to its caller.

## Technical Details

### Files on a host

- `~/.config/ferry/config.toml` - this host's config.
- `~/.local/state/ferry/` (mode 0700) - `ferry.sock` (the daemon socket, mode 0600), `ferry.lock`, `ferry.log` (stderr of a daemon started by `ferry peer`).
- The handler folder named by `handlers` in the config.
- The socket path is checked against 103 bytes: macOS has a 104-byte `sun_path` and std needs room for the terminating NUL. Past that the daemon exits with `ferry: socket path <path> is <n> bytes, at most 103 fit`. The same limit applies on Linux, which allows more.

### config.toml

All keys are optional. Unknown keys are an error (`#[serde(deny_unknown_fields)]`), so a typo fails loudly.

| Key | Type | Meaning |
|---|---|---|
| `handlers` | string | Folder with this host's handlers. A leading `~/` expands to `$HOME`. Absent: this host has no handlers. |
| `connect` | string | ssh destination. Present: this host is the dialer. |
| `remote_ferry` | string | Path of `ferry` on the far host, default `ferry`. Needed when sshd's PATH does not contain it. Only read with `connect`. |
| `[[listen]]` | table array | Each has `port` (1-65535) and `handler` (a name on the other side). |

Example of a far host:

```toml
handlers = "~/.config/ferry/handlers"

[[listen]]
port = 7811
handler = "service-proxy"
```

### Handlers

- A handler is a regular file in the handler folder with an execute bit for the user, carrying the marker line `# @ferry.name <name>` within its first 64 lines. An optional `# @ferry.desc <text>` after it is its one-line description. Files without the marker are not handlers. A compiled program becomes a handler through a small script with the marker that `exec`s it.
- A name is 1 to 64 characters of `[a-z0-9._-]`, starting with a letter or digit (`HandlerName` newtype). A file with an invalid name, or a second file with a name already taken (in file name order), is skipped with a warning in the daemon log and in `ferry ls`.
- The contract: argv from the call, stdin from the caller, stdout is the answer, stderr is the error text, the exit code is the result. A handler must not wait for a person: it has no terminal.
- A `desc` longer than 200 bytes is cut to 200 bytes at a character boundary. A host offers at most 256 handlers: files past that in name order are skipped with the reason `too many handlers`. With the 64-character name this keeps `hello` far below the line limit.
- The daemon spawns the handler in its own process group (`process_group(0)`), so cancel reaches the programs it starts too.
- A run ends when the handler process has exited and both its stdout and stderr have reached EOF. If a descendant still holds them open 5 s after the handler exited, the daemon runs the cancel sequence on the group. If they are still open at the sequence's last step, a process outside the group holds them (it called `setsid` or daemonized itself), and that step closes the daemon's own ends of the pipes and ends the run: whatever that process writes later is lost. So a run ends at most about 15 s after the handler exits: 5 s of waiting, then the 10 s cancel sequence. `exit` is sent after the `eof` of both streams, and only then does the call free its place among the 32. A handler that starts a long-lived background program redirects that program's stdio.

### Frames

One JSON object per line, `kind` names the frame. A line longer than 128 KiB is a protocol error and closes the link. A sender never produces one: before sending `open` it measures the encoded line, and an `open` over 128 KiB fails that call locally with 255 `arguments too large` without touching the link. `chunk` data is capped at 64 KiB raw and the handler list is capped (see Handlers), so no other frame can reach the limit. A line that is not valid JSON or lacks `kind` closes the link too. A well-formed frame of an unknown kind is skipped.

| Frame | Fields | Direction and meaning |
|---|---|---|
| `hello` | `version` (1), `kinds` (names this side speaks), `handlers` (`[{name, desc}]`) | First line from each side. A different `version` closes the link with a logged error. |
| `handlers` | `handlers` | The sender's new list after `ferry reload`. |
| `ping` | - | Every 10 s from each side. |
| `open` | `id`, `name`, `argv` | Opens a call on the receiver. |
| `chunk` | `id`, `stream` (`stdin`, `stdout`, `stderr`), `data` (base64, at most 64 KiB raw) | `stdin` from the caller, `stdout` and `stderr` from the handler. |
| `eof` | `id`, `stream` | That stream of the call is finished. The others stay open. |
| `exit` | `id`, `code` | The handler exited. The last frame of the call. |
| `error` | `id`, `code` (127, 126, 255), `message` | The call failed before or instead of an exit. The last frame of the call. |
| `cancel` | `id` | The caller went away. The receiver stops the handler. |

- Call ids are `u64`. The dialer opens odd ids starting at 1, the far host even ids starting at 2, so a `chunk` id is never ambiguous.
- A frame for an unknown or finished id is dropped.

### Errors and exit codes of `ferry call`

| Case | Exit code | stderr |
|---|---|---|
| Handler exited | the handler's code | the handler's own stderr |
| No handler with that name on the other side | 127 | `ferry: no handler <name> on the other side` |
| The handler file could not be started | 126 | `ferry: cannot start <name>: <reason>` |
| Link not up, link lost during the call, unread limit passed, 33rd concurrent call, arguments over 128 KiB | 255 | `ferry: <reason>` |

A handler killed by a signal is reported as `exit` with code 128 + signal number. A listen port has no exit code: on any of these errors the daemon closes the TCP connection.

### Limits and timers

- Chunk: 64 KiB of raw data. Line: 128 KiB.
- Unread bytes per call: 16 MiB.
- Handlers running at once on one host: 32. The 33rd `open` is answered with `error {code: 255, message: "too many calls"}`.
- Ping: every 10 s from each side. No frame received for 30 s: the link is lost.
- Link lost: every call in flight ends with 255 on both sides, and their handlers get the cancel sequence.
- Cancel sequence, timed from its start t0: SIGTERM to the handler's process group at t0. At t0 + 5 s, SIGKILL to the group if any member is still alive (`kill(-pgid, 0)` succeeds), whether or not the handler itself has already exited. At t0 + 10 s, whether or not a SIGKILL was needed, the daemon closes its ends of any handler pipe still open and ends the call. Every call therefore ends within about 10 s of a cancel or a link loss.
- Handler description: 200 bytes. Handlers per host: 256.
- Dialer reconnect: 1, 2, 4, 8, 16 s, then every 30 s without end. The schedule restarts after a link that completed `hello`.

### The dialer's ssh

`$FERRY_SSH -T -o BatchMode=yes -o ConnectTimeout=5 <connect> <remote_ferry> peer`, where `FERRY_SSH` defaults to `ssh`. `BatchMode` turns a host-key or password prompt into a failure instead of a hang. The ssh child's stderr goes to the daemon log, one line per failed attempt.

### The local socket

The daemon socket serves three kinds of clients. The first line a client sends (at most 128 KiB, like every line) names its kind. The daemon answers with one reply line, `{"ok":true}` or `{"ok":false,"code":<n>,"error":"<text>"}`, and closes the connection after a refusal.

- `{"kind":"peer"}` - a bridge. Refused with code 255 only while the daemon shuts down. After `{"ok":true}` the connection carries the link's frames, starting with the daemon's `hello`. A new peer while one is connected replaces it: the old link is dropped as lost.
- `{"kind":"call","name":"...","argv":[...]}` - `ferry call`. Refused with code 255 and the reason when the link is down, the call limit is reached or the `open` would exceed 128 KiB. After `{"ok":true}` the client and the daemon exchange the `chunk`, `eof`, `exit` and `error` frames of this one call with the same codec, always with `id` 0: a local connection carries exactly one call, and the daemon maps it to the link id it allocated. The client closing the socket before `exit` or `error` is a cancel.
- `{"kind":"ls"}` - the reply is `{"ok":true,"link":...,"local":[...],"remote":[...],"skipped":[...]}`, then close. `link` is `{"state":"up","version":1}` or `{"state":"down","reason":<last failure as a string, or null>}`. `local` and `remote` are lists of `{"name","desc"}`, `remote` empty while the link is down. `skipped` is a list of `{"file","reason"}` for this host's folder.
- `{"kind":"reload"}` - the daemon re-scans its folder, sends `handlers` if the link is up, and replies `{"ok":true,"handlers":<count>,"skipped":[{"file","reason"}]}`.

A client reads the reply line one byte at a time up to the newline, because a buffered reader would swallow frames that follow it in the same read. `ferry peer` writes to its stdout only the bytes after the reply line. The 128 KiB line limit applies to every line on the link and to the first line a client sends. The `ls` and `reload` replies are the last line before the daemon closes, so the client reads them to the end of the connection and applies no limit: with 256 handlers on each host and a long `skipped` list they can exceed 128 KiB.

### Listen ports

- An accepted connection opens a call to the listed handler with no argv. While the link is down the connection is closed at once.
- Bytes read from the socket go out as `chunk stdin`. A read that returns EOF sends `eof stdin` and never `cancel`, so a client that half-closes after its request still gets the answer.
- `chunk stdout` is written to the socket, `chunk stderr` to the daemon log. `eof stdout` shuts the socket down for writing, so the client sees EOF while it can still send. A failed write to the socket means the client is gone and cancels the call. `exit` or `error` closes the socket.
- A handler that stays silent after its client left keeps its call until it writes or exits. v1 accepts this: a closed TCP peer is only visible on the next write.

### CLI

- `ferry daemon` - runs the daemon in the foreground. launchd or a shell runs it on the dialer, `ferry peer` on the far host.
- `ferry peer` - the bridge that sshd runs.
- `ferry call <name> [args...]` - calls a handler on the other side.
- `ferry ls [--json]` - link state (`up` with the peer's version, or `down` with the last reason), this host's handlers, the other side's handlers from its last `hello` or `handlers`, and the skipped files with the reason.
- `ferry reload` - re-scans the handler folder and sends `handlers` to the other side.
- `ferry help` - usage.

### Task 6: Session over a link

- Create: `src/session.rs`, `src/writer.rs`
- Modify: `src/lib.rs`

- [x] `writer.rs`: one task owning the write half. Link frames (`hello`, `handlers`, `ping`) are always written first (`biased` select).
